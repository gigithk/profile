AI Copilot UX Architecture Proposal

A UX architecture proposal for an engineering copilot, connecting question intent to response rules and exploring clearer system feedback, project context, connected workflows, generated documents and knowledge boundaries.

The problem was not simply that answers were too long. The product needed to understand what kind of question it had received before deciding how to answer.

This proposal explored conversational AI in a specialist engineering context. The review examined the experience around chat, project knowledge, connected tools and generated documents rather than only the visual interface.

One recurring problem made the larger issue visible: a question that called for a direct yes or no could receive a long paragraph instead. The response could contain relevant information and still fail the user's immediate need.

How I contributed

As UX architect, I connected issues that would otherwise appear as separate UI observations: response structure, project context, agent selection, tool access, generated files and knowledge sharing.

The output was an experience proposal that made the product logic visible enough for design, product and engineering teams to discuss and detail together.

  • Review the end-to-end copilot experience as a UX architect
  • Identify where response behaviour and user intent diverged
  • Define an initial question taxonomy and response rules
  • Map interaction improvements across chat, projects, tools and documents
  • Communicate the proposed experience as one connected system
Proposal scope

This case documents an expert UX architecture review and proposed direction. Internal product names and screens have been removed. It does not claim implementation, validation or measured product outcomes.

Frame the challenge

A proposal for specialist engineering work.

The experience combined chat with project-specific knowledge, documents, diagrams, context information and potential external tools. Users could ask direct questions, work within a project or invoke a connected capability.

That made the quality of the interaction dependent on more than language generation. The system also needed to select the right context, explain what it was doing and present the result in a form suited to the task.

Relevant information was not always a useful answer.

A simple protocol-support question could produce a large explanatory paragraph before resolving the basic yes-or-no need. The answer might be technically rich, but its shape did not match the question.

The same response pattern could not serve every intent. A procedure needs steps. An underspecified request needs clarification. A decision needs comparison and recommendation.

Before improving the prose, determine the kind of answer the user needs.

In an engineering context, answer shape affects confidence.

Users need to scan, verify and act. A verbose response can hide the decision, while an overconfident response can hide uncertainty or missing context.

The review therefore treated concision, clarification, source visibility and system feedback as part of trustworthy product behaviour rather than cosmetic polish.

This was an expert review, not a validation study.

The available material supported an architectural review of the product experience and a proposal for improvement. It did not include direct user-research evidence, implementation evidence or post-release measurement.

The work therefore focused on making interaction risks, response rules and system boundaries explicit enough for subsequent product, engineering and research decisions.

Build understanding

Classify the question before generating the answer.

I proposed an initial set of question types that could act as a routing layer between the user's prompt and the response design. The taxonomy was intentionally practical: each class mapped to a recognisably different answer behaviour.

This changed the design question from ‘How should the chat look?’ to ‘What response contract should the system follow for this intent?’

Four intents, four different response contracts.

Dichotomous questions begin with a clear yes or no, followed by explanation and conditions only when needed. Procedural questions provide step-by-step guidance.

Vague questions ask for missing critical information or state assumptions in a structured overview. Decision questions compare options and make a recommendation.

This taxonomy was a design hypothesis from the expert review. It would need validation against real questions and user behaviour before becoming a production classification model.

  • Direct: resolve first, explain second
  • Procedural: sequence the work
  • Vague: clarify or expose assumptions
  • Decision: compare and recommend

Make the copilot concise, visible and appropriately uncertain.

The review established supporting rules: keep answers natural and conversational, avoid a robotic tone, be concise but clear, and ask a follow-up question when confidence is low.

It also proposed showing the system's progress and sources so users could understand what had been reviewed or selected without being forced to read internal reasoning.

Make the key decisions

Let users see and act on what the system produced.

The proposal added lightweight feedback around system activity and actions on a response, including copy and feedback controls. Content could be classified as a table, timeline or text so the interface could use an appropriate template.

For generated documents, a split view could keep the conversation and generated output in context instead of forcing a download-and-switch workflow.

Context needed permissions, not just retrieval.

The proposal distinguished project knowledge from published knowledge and considered global, regional and people-specific access. It also showed how system-generated documents could be added back to a knowledge base.

This made knowledge sharing and reuse an explicit experience decision rather than an invisible backend behaviour.

Shape the solution

Move from chat answers to connected product work.

The review explored selecting or creating a project from the conversation, attaching files and invoking connected capabilities. A specification-checking flow could request the required file, use existing project context and generate a compliance output.

These directions positioned the copilot as a coordinator of context and tools, while keeping the user's project and current task visible.

Outcome and reflection

A set of issues became a coherent product direction.

The review connected conversational quality, response templates, project context, tool invocation, document workflows and knowledge boundaries in one experience map.

That artefact created a shared starting point for prioritisation and detailed design. The supplied material does not document implementation or measured user outcomes, so this case presents the work as a proposal rather than a shipped result.

UX architecture turns AI behaviour into a designable system.

The work demonstrates the ability to move between a precise usability problem and the larger product architecture around it. It translates observations into rules, patterns and cross-functional decision points that a team can act on.

  • Diagnosing beyond surface-level UI
  • Structuring AI responses around intent
  • Designing agentic and document workflows
  • Making trust and access boundaries visible

The best AI answer is not always the most complete one.

Usefulness comes from matching the response to the user's intent, confidence and next action. In AI products, designing that match is as important as designing the interface that displays it.
